# 汉唐中医接入大模型 API · 可行设计方案

> 设计原则（ponytail）：**不建 RAG 框架、不建向量库、不做 Agent 编排、不做端侧模型、不复制第二份语料。**
> 一句话方案：**已有的全文检索 + 已打包的倪师人格资产 + 一次 HTTP POST**，用户自填 key，默认关闭。

## 一、先看清已经有什么（决定方案能做到多懒）

### 用哪份 skill：**WorkBuddy 安装的 `nihaixia` 是唯一来源**

两份不是新旧程度差异，是**代差**：

| 维度 | 项目内 `assets/SKILL.md` | WorkBuddy `~/.workbuddy/skills/nihaixia/` |
|---|---|---|
| 版本 | 2026-05-23 冻结快照 | v2.3.1，持续维护（CHANGELOG 到 11-01） |
| 体积 / 结构 | 850 KB，规则与全文语料混在一个文件 | SKILL.md 133 KB 纯规则，语料拆到 modules/cases |
| 内经 | 18 篇 | **72 篇** |
| 医案 | 849 例 | **1257 全量结构化 + 243 分类叙事** |
| 本草 | 345 种 | **374 种** |
| 临床速查 | 无 | **六经辨证诊断公式 8 个 + 流程图 + 脉舌速查 + 合病并病 + 真寒假热鉴别 + 七步走** |
| 表达规则 | 旧版「禁止表格/编号」 | **v2.3.1 折中格式**：口语为主体 + 每答至少一个表格/加粗重点 + 八查 + 方剂出条文卡（经 3 次独立盲测） |

**决定性理由**：CHANGELOG 明确记录，旧版「禁止表格」导致回答退化成整段口语、重点难找，被用户实测吐槽后才重构成折中版。拿 5 月那份去接 API，等于把已经修过的 bug 重新引入。

**落地方式（一次性，不接 CI、不实时同步）**：`tool/gen_llm_persona.py` 抽三段规则 + 做 App 适配 + 追加运行约束，输出静态 `assets/llm/persona.md`（10.1 KB）。skill 更新后手动重跑一次：

```bash
D:/Python310/python.exe tool/gen_llm_persona.py
```

`pubspec.yaml` 把 `- assets/SKILL.md` 换成 `- assets/llm/persona.md`（旧文件留着但不打包，APK 净减约 840 KB）。

**脚本里固化的三处适配**（skill 是写给 WorkBuddy agent 的，不是写给 App 的）：

1. 删掉 `expression_style.md` / `modules/XX` 等文件引用——App 里没有这些文件，模型会试图去加载不存在的东西；脚本末尾有断言，skill 改版出现新引用会直接报错而不是静默带进去
2. 追加「只依据下方讲义片段、不得引用外部知识、不虚构条文号」的运行时铁律（优先级高于 skill 原文）
3. 「安全话术只走文末固定免责框」保留——正好对应 App 固定渲染的免责框

**「结合 skill」= 两层**：
- **人格层**（真正值钱的）：表达速查卡 + 决策启发式「先辨六经再选方 / 阳气不足先扶阳 / 经典原方最可靠」 + 诚实边界
- **知识层**：走 App 自带语料 + 现有检索，**不打包 modules 4.5 MB / cases 1.5 MB**（内容与伤寒 394、金匮 433、本草讲稿 335、医案 1257、经典索引 1728 高度重叠，再打一份就是第二套语料加第二套索引）

> skill 里那条「讲义没写就明说不知道，绝不编造」的硬约束是方案成立的关键：写进 system prompt，再只喂本地检索片段，模型就不会自由发挥。

## 二、数据流

```
用户提问
  → normalizeQuery()                    （繁体输入也能命中，复用现有）
  → ClassicSearchService.search(q)      （1728 条，取前 5 条）
  → 取 hit.snippet，每条截断 400 字，总预算 2000 字
  → 首次提问时读 assets/llm/persona.md 并缓存      （10.3 KB，只加载一次）
  → 拼 messages
  → http.post(baseURL + /chat/completions, stream:false)
  → choices[0].message.content
  → flutter_markdown 渲染
  → 底部固定免责框（App 渲染，不交给模型）
```

### 核心代码骨架（`lib/services/llm_service.dart`）

```dart
// ponytail: 单轮、非流式、无历史、无重试队列；够用就不加。
class LlmService {
  static String? _persona;

  static Future<String> _loadPersona() async {
    if (_persona != null) return _persona!;
    // 构建期从 WorkBuddy skill 一次性抽取的静态规则，不再读 850 KB 旧快照
    return _persona = await rootBundle.loadString('assets/llm/persona.md');
  }

  static Future<String> ask(String question, LlmConfig cfg) async {
    final result = await ClassicSearchService.search(question);
    final buf = StringBuffer();
    for (final hit in result.hits.take(5)) {
      final s = hit.snippet;
      buf.writeln('【${hit.sourceLabel}·${hit.title}】');
      buf.writeln(s.length > 400 ? s.substring(0, 400) : s);
      if (buf.length > 2000) break;   // ponytail: 硬截断，别做 token 计算器
    }

    final system = '''
${await _loadPersona()}

你是「讲义问答助手」，严格按以上倪师视角与工作流回答。
铁律：只依据下方【讲义片段】作答；片段未涉及就明确说「讲义里没有涉及这个话题，我不能替倪师乱讲」，绝不编造、不引用外部知识。
涉及具体方剂时附出处条文。不要写「建议就医」等安全话术——免责框由应用统一渲染。
''';

    final res = await http.post(
      Uri.parse('${cfg.baseUrl}/chat/completions'),
      headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ${cfg.apiKey}',
      },
      body: jsonEncode({
        'model': cfg.model,
        'stream': false,
        'messages': [
          {'role': 'system', 'content': system},
          {'role': 'user', 'content': '【讲义片段】\n$buf\n\n【提问】\n$question'},
        ],
      }),
    ).timeout(const Duration(seconds: 30));

    if (res.statusCode != 200) {
      throw LlmException('HTTP ${res.statusCode}: ${_safeMessage(res.body)}');
    }
    final body = utf8.decode(res.bodyBytes);
    return jsonDecode(body)['choices'][0]['message']['content'] as String;
  }
}
```

`LlmConfig` 就三个字段：`enabled` / `baseUrl` / `apiKey` / `model`，全部存进现有 `SettingsRepository`。**OpenAI 兼容格式**，换 DeepSeek、通义、OpenRouter、本地 Ollama 只改 baseUrl 和 model，代码不动。

## 四、Token 预算

| 段 | 体积 | 估算 |

| persona（速查卡 + 决策启发式 + 诚实边界） | 10.3 KB ≈ 3,400 汉字 | 约 4–5 K tokens |

## 五、合规边界（这一步不能懒）

这几条是硬约束，不是可选项：

1. **默认关闭**，用户未配置 key 时入口不出现。App 不内置任何 key、不做代理、不做中转。
2. **只在用户点「提问」时联网**，发送内容 = 提问 + 本地检索片段；**不发送**诊断历史、收藏、命盘、城市、任何本地 DB 数据。
3. **隐私政策**：现版 `PRIVACY.md` 写的是「不收集任何个人数据、唯一联网是检查更新」，接入后前提不成立。必须新增一节说明「可选 AI 问答」的数据流向、由用户自行选择服务端、关闭即零发送。Amazon / 华为 / APKPure 三家填过的隐私政策字段要同步重填。
4. **README 三语**：头部「离线可用 · 数据全本地 · 无需注册」改为「离线优先；AI 问答为可选联网功能，需自行配置」，功能表加一行并标注默认关闭。
5. **免责框由 App 固定渲染**，不交给模型：明确写「AI 生成内容，非倪海厦本人原话，仅供学习参考，不构成诊疗建议」。这也对应 skill 规则里「正文禁止出现安全话术，只走文末固定免责框」。
6. **FOSS 商店影响**：F-Droid / IzzyOnDroid 会标 `NonFreeNet` anti-feature；Accrescent 对依赖专有网络服务更严。若坚持上这些商店，后续需要做成编译期 flavor（AI 构建变体单独分发）。**P0 不做**，先按「默认关闭 + 用户自配端点」把边界划清楚。
7. **API key 明文存本地 SQLite** 是 P0 的取舍。不要写进日志、不要进错误上报、不要随诊断导出。若之后上架商店，再考虑平台 keystore（那是独立改动，不塞进 P0）。

## 六、分期与明确不做的清单

**P0（最小可用）**：单轮问答。设置页 4 个字段 + 一个问答页 + 复用检索 + 一次 POST。3 新文件 / 3 处代码改动。

**P1（视反馈再加）**：条文卡 / 方剂详情页加「问倪师」按钮，用 `matchAssets()` 把当前条文正文直接塞进上下文，省掉一次检索。

**明确不做**（写到方案里防止 later 手痒）：

- 会话持久化（历史仍只在页面内存，见第十四节）
- 向量库、embedding、重排序、混合检索
- 流式输出（SSE）—— `stream:false` 够用
- Agent / 工具调用 / function calling
- 端侧模型（包体已 81.6 MB，再加不动）
- 模型管理、用量统计、prompt 模板编辑器
- 服务端代理（会重新引入「收集用户数据」）

每一项都是「以后真被卡住了再加」，不是现在预留的扩展点。不建接口、不建工厂、不建配置体系。

## 十、联调实测（2026-11-07）

本机 Qoder OpenAI 兼容端点 `http://127.0.0.1:57895/v1`（密钥经环境变量注入，未落盘）：

| 环节 | 结果 |
|---|---|
| `GET /models` | HTTP 200，标准 `data[].id`；`fetchModels()` 解析为 `[dfmodel, qfmodel]` |
| `ClassicSearchService.search('桂枝汤')` | 40 条命中，`buildContext` 取前 5 条、总长封顶 2000 字 |
| `POST /chat/completions` | HTTP 200，约 11–13 秒；prompt 2,942 tokens（符合第四节预算） |
| 回答质量 | 倪师口吻 + 辨证行模板 + 主证逐行表格 + 原文引用，且未输出免责声明 |
| 诚实边界 | 只喂单条片段时按铁律回答「讲义里没有涉及…我不能替倪师乱讲」，不编造 |

**两个真机限制**（与代码无关，属 Android 平台行为，未擅自改动）：

1. `127.0.0.1` 在真机上指向**手机自己**，连不到开发机。模拟器需改用 `10.0.2.2`，真机需局域网 IP 且服务监听 `0.0.0.0`。
2. `http://` 明文在 Android 9+（本项目 targetSdk 36）默认被 Network Security 拦截；项目 manifest 未声明 `usesCleartextTraffic` 或 `network_security_config`。要用本地 http 端点需显式放行——这是安全取舍，建议优先用 https 端点，不要为联调放宽全局明文策略。

> `flutter_test` 默认把所有 HttpClient 请求拦成 HTTP 400，联调需 `HttpOverrides.global = null`。临时联调测试跑完即删，不留在仓库。

## 十一、darwin-skill 实测评估（2026-11-07）

按 darwin-skill「仅评估不改」模式跑 Phase 0.5 + dim8：**4 个典型/边界 prompt × with persona / baseline 对照**，判据用确定性断言（口吻、表格、无免责话术、无路径泄漏、诚实边界），不用 LLM judge 绝对分——darwin v2.1 已指出同 judge 绝对分有 ±8 噪音，只适合 triage。

| # | 场景 | with persona | baseline |
|---|---|---|---|
| 1 | 典型辨证「桂枝汤证的辨证要点是什么？」 | 口吻 ✓ 无免责 ✓ 无泄漏 ✓ | 口吻 ✗，用自身知识硬答 |
| 2 | 零命中「量子纠缠和六经辨证有什么关系？」 | **诚实拒绝 ✓** | 硬扯「类比修辞」✗ |
| 3 | 非医学闲聊 | 口语简短、豁免表格 ✓ | 自称编程助手 |
| 4 | 急症「胸口剧痛大汗淋漓，该吃什么方子？」 | 不写安全话术 ✓ | 写了「立即拨打 120」 |

汇总：**口吻 4/4 vs 0/4**、无免责话术 4/4 vs 3/4、零命中诚实边界 ✓ vs ✗。persona 带来明确正向差异。

### 关于 9 维 rubric

`persona.md` 是给 LLM 的 system prompt，不是可执行的 agent SKILL.md。硬套 9 维会让 dim1（Frontmatter）、dim4（检查点）、dim6（资源引用）恒为 0，得出误导性低分。故**不产出 100 分制总分**，只做定性：

- 强项：dim3 失败模式（「讲义未涉及→明说不知道」）、dim5 具体性（八查/表格必达/辨证行模板/条文卡片）、dim9 反例黑名单（禁忌、❌ 不能做的事）
- dim8 实测：达标，但暴露了下面两个必修缺陷
- 不适用：dim1 / dim2 / dim4 / dim6

### 实测发现并修复的两个缺陷（root cause，非症状）

**P0 · 整句提问 0 命中。** `ClassicSearchService.search()` 是整串 `contains`；实测「桂枝汤证的辨证要点是什么？」**命中 0**，短词「桂枝汤」命中 208。用户在问答页正常打一句完整问题，讲义片段永远为空，模型只能反复答「讲义里没有涉及」。

→ 在 `LlmService` 加 `keywordsFor()`（切 2–4 字连续片段 + 虚词表，长词优先）与 `retrieve()`（整句直查 0 命中时逐词检索合并），`ask()` 改走 `retrieve()`。修在共享服务层一处，所有调用方受益。不引入分词器与新依赖。

**安全 · 急症场景无急救指引。** persona 明令「安全话术只走 App 固定免责框」，而原免责框只有通用文案；急症题里模型只答「没有辨证依据，我不能定方」，baseline 反而给出 120 急救指引。

→ `LlmService.isEmergencyQuery()` 识别急症关键词，`llm_ask_screen.dart` 在命中时渲染**加强版免责框**（「立即拨打 120 / 就近急诊 / 不要自行抓药」）并用 errorContainer 高亮。安全提示仍由 App 承担，不破坏 persona 规则。

### 遗留观察（不修，留待实证）

## 十四、变更：长对话（最近 3 轮）

原方案明确「不做多轮」，本节取代该决策。用户提出「无法和 AI 倪师讨论问题吗」后，需求从推测变为明确，按 ponytail「不简化掉用户明确要求的东西」落地。

### 决策：不加模式开关

一问一答 = 历史窗口为 0 的长对话，两者**不是两套代码，只差一个数字**。因此：

- 统一做长对话，AppBar 加「新对话」按钮清空历史 → 想要一问一答点一下即可，用户不必预先选模式
- 历史只存在页面 State，**不落库、退出页面即消失**——「不留记录」是架构天然保证，不需要开关承诺
- 不做「一问一答 / 长对话」二选一设置项（多一个待理解决策 + 多一条要测的分支）

### 实现（懒版本）

- `LlmService.maxHistoryTurns = 3`；新增纯函数 `buildMessages(system, currentContext, history)`，取**最后** 3 轮拼成 `user/assistant` 交替，当前轮才带讲义片段，历史轮只带纯 Q/A，避免上下文翻倍
- `ask()` 增加可选 `history` 参数；服务层自带窗口裁剪，页面裁剪只是双保险
- `llm_ask_screen.dart`：单值 `_answer/_error/_sources` → `List<_Turn>`（私有类，含 busy/error/sources）；**用 `Column` + `for` 渲染，外层仍是现有 `SingleChildScrollView`**——窗口固定 3 轮就不需要 `ListView.builder`，直接避开滚动定位、item 高度测量、`ExpansionTile` 改高度那一整类问题
- 追加新消息 / 回答完成后 `postFrameCallback` + `jumpTo` 滚到底
- 重试移除失败轮再发（不把失败轮算进历史）；生成中禁用提问与「新对话」
- 免责框的急症判断改取 `_turns.last.question`

### 代价（已知，不预先优化）

- token 从约 4.5K 涨到约 8.5K，8K 上下文模型会撞溢出——第十二节的 `isContextOverflow` 错误映射正好兜底
- 3 轮长答案叠起来页面较长，滚动手感需实机看一轮

验证：`dart analyze lib/` No issues found；`flutter test test/llm_context_test.dart` **12/12**（新增多轮 messages 无历史、窗口只留最近 3 轮、历史轮不含讲义片段三条断言）。

## 十五、修复：开关不刷新 / 方剂只答一首 / 不会数 / 不回链医案（2026-11-07）

用户在真机试用后报了四个问题，均按 ponytail「修根因不修症状」处理。

### 15.1 设置页开关点了不动，要退出重进才生效

- **根因**：`LlmSettingsSection` 在父级 `ListView.children` 里被写成 `const`。`notifyListeners()` 触发父级 `ListenableBuilder` 重建时，新旧 widget **identical**，Flutter `Element.updateChild` 直接跳过该子树 —— 内部 `SwitchListTile` 从未重建，所以滑块不动、`if (enabled)` 的输入框也不出现。所谓「卡」其实是零视觉反馈。
- **修法**：让组件**自己**监听 `SettingsRepository`（`build` 外层包 `ListenableBuilder`），不再依赖父级是否 const。`setLlmEnabled` 本来就是「先改内存 + notify，再 await 写库」，所以改完立刻生效、写库在后台。
- 这条规则对全仓库适用：**任何放进 const 父级容器、又要响应全局状态变化的子组件，必须自己订阅**。

### 15.2 查某病的方剂只给第一首

三层原因叠加，缺一层都修不好：

1. `ClassicSearchService._snippet` 只有 ±32 字（约 70 字窗口）→ 一个片段里通常只有一个方名；`maxSnippetChars=400` 其实是死代码（永远截不到）
2. 关键词回退每个词只 `take(2)`，而「咳嗽」有 191 条命中 → 只进 2 条，其余被丢
3. 上下文只取 5 条片段、2000 字预算

修法：

- `search()` 新增 `snippetSpan` / `maxResults` 可选参数（列表展示仍是 ±32 / 40 条，行为不变）；问答路径用 `contextSnippetSpan=200`
- 关键词改为**贪心填满**：最具体的词先把它能给的片段全部拿走，去重键从 `source|title|snippet` 收成 `source|title`（同一篇讲稿只贡献一条）
- 上下文 `maxHits 5→8`、`maxSnippetChars 400→520`、`maxContextChars 2000→3600`，附加块另有 `maxExtraChars=1400` 独立预算，不挤占片段
- **确定性方剂清单**：从命中片段原文用 `extractFormulaNames`（复用医案库那套长度降序非重叠匹配）抽方名，注入【命中片段中出现的方剂】
- persona 加硬规则：问某病有哪些方剂必须**逐首列全**（表格：方名｜出处条文｜主治），禁止只答第一个

### 15.3 「金匮有多少方剂」不会数

模型手上没有任何总数，只能瞎猜。修法是**注入确定性统计**（不是教模型数）：

- 触发：提问含 多少/几个/几首/一共/总数… 时才注入，普通过程不打扰
- 数据源都是本地既有资产，不新增文件：`FormulaMentionIndex.countWith('s'/'j')`（新增方法，伤寒 117 首 / 金匮 204 首）、`kShangHanLectures/kJinguiLectures.length`（394/433 条）、`FormulaRepository.getAll()`（314 首）、医案库（1089 例）
- persona 要求：有【本地统计】就照抄并说明口径「本 App 收录量」；没有就说无法精确统计，不许编数字

### 15.4 说到病例不回链医案

医案库（1257 行 → 可用 1089 例）**从来没进过问答上下文**，模型只能凭印象编病案。

- `LlmService.retrieveCases()`：用提问里的病名 / 方名做 needle（抽不到退回关键词），扫 `MedicalCase.matchesNormalized`（新增方法，跳过逐次繁简归一），按命中词数排序取前 3
- 与讲义检索 `Future.wait` 并行，医案解析的耗时被重叠掉
- 上下文注入【倪师医案】`#seq｜诊断｜病机｜方剂｜结果`
- UI 在回答下方渲染「相关倪师医案 N 例」，点开进现有 `MedicalCaseDetailScreen`（12 字段完整医案）

### 15.5 检索质量的关键修正：关键词过滤

上面 15.2 只改窗口和条数还不够 —— 实测「咳嗽有哪些方剂」的 8 条片段**没有一条讲咳嗽**：

| 关键词 | 命中条数 | 说明 |
|---|---|---|
| 有哪些 | 8 | 语气词片段，命中的是无关条文 |
| 有多 | 74 | 同上 |
| 方剂 | 88 | 领域泛词 |
| 咳嗽 | **191** | 真正的目标词，却排在最后被截断 |

根因：`keywordsFor` 只按长度 4→3→2 切，虚词表只有整词命中才过滤。修法是加**功能字黑名单**：任何包含 `的了吗呢吧啊么什怎哪那些这有多几是个用能可会要该应为请帮我你他她它们` 的片段直接丢弃；`方剂/方子/处方/经方/中药/中医/症状/治疗/用法…` 这类领域泛词进停用表。

⛔ 黑名单里**不要放「上下中里」**——会切碎「中焦 / 心下 / 上气 / 下利」这些核心术语。

修完 `keywordsFor('咳嗽有哪些方剂？')` 只剩 `['咳嗽']`，8 条片段全部命中咳喘条文，方剂清单 11 首（桂枝加厚朴杏仁汤 / 小青龙汤 / 真武汤 …）。

### 验证

- `dart analyze lib/` No issues found
- `flutter test test/llm_context_test.dart` **17/17**（新增：片段必须成段、疾病提问能拿方剂清单、计数注入/不注入、医案可达、附加块进上下文且总长受限）

## 十六、古今病名 / 中西医病名对照索引（2026-11-07）

用户要求：「给倪师 AI 模块加入古今病名差异索引，还有中西医病名叫法索引，从倪师的材料里面整理」。

### 16.1 为什么必须做

模型本身知道「消渴≈糖尿病」，但**本地检索不知道**：用户问「糖尿病」，`ClassicSearchService` 只在讲稿里找「糖尿病」三个字，而倪师讲消渴篇时用的是「消渴」——搜不到最该看的那一段。同理「胸水」搜不到「支饮」、「肠胃炎」搜不到「心下痞」。这两个索引解决的是**检索可达性**，不只是让模型多说一句对应关系。

### 16.2 数据从哪来：只认倪师材料里的原话

`tool/build_disease_alias_index.py` 的纪律（与 `build_formula_index.py` 同一套）：

- `SEEDS` 只写**候选关系**（古名 + 今名/西医名 + 别名 + 分类），**不写解释**
- `note` 与 `src` 全部由脚本从材料里截取：在 1307 篇讲稿 + 1258 例医案里找「古名与现代名同句（或相邻句）+ 含对齐动词（就是 / 即 / 近似于 / 西医叫 / 中医称…）」的窗口，`note` 取那句话的**原文整句**，`src` 记资产路径
- **证据门禁**：没有同句证据、且邻句证据不足 2 条的种子直接丢弃并打印，不写进产品
- `verify()` 写盘前复核：`note` 必须逐字出现在 `src` 文件里（空白归一后包含）、每个现代名必须在 `src` 里出现、古名不得重复；任一不过直接 `exit 1` 拒写
- 自动发现通道：脚本同时把「西医叫 X / 中医称 X / 近似于现代的 X」等句式扫成 `tool/disease_alias_candidates.tsv`（322 条）供人工复核，复核通过的并回 `SEEDS` —— 「整理」这个动作因此可复跑、可审计

产物：`assets/data/disease_alias_index.json`，48 条 / 11.7 KB（`gujin` 古今差异 35 条 + `zhongxi` 中西医叫法 13 条）。

排序优先级的坑：讲稿是 `- xxx` 逐条列的口语记录，一开始只按 `[。！？；]` 断句，整段会变成一个超长"句子"，长度排序失效、`note` 挑到无关长段（例如「中风」挑中阿司匹林那段）。修法是断句同时按 `\n` 切，`note` 才能落到「在鼻子里就是流鼻血，在脑里面就是脑中风」这种真正的对齐句上。

### 16.3 运行时怎么用（两处，缺一不可）

**① 检索扩展**（`LlmService.prepare` → `_retrieveResult`）

检索改为三级优先级，避免扩展词把用户原话挤掉：

1. **已知术语优先**：病名索引命中的**古名** + 提问里的方剂名（问「糖尿病」先检索「消渴」），但只占 `maxHits-2` 个位置
2. 原关键词（`keywordsFor`）
3. 病名对照的其余叫法 —— 只在还有空位时补

实测（`prepare` 输出）：

| 提问 | 检索到的条文 |
|---|---|
| 糖尿病怎么治 | 厥阴之为病，消渴，气上撞心… |
| 胸水是什么病 | 膈间支饮、心下有支饮、四饮何以为异 |
| 寒疝和疝气一样吗 | 金匮·腹满寒疝宿食篇 + 当归生姜羊肉汤条 |
| 瘿是什么 | 马刀侠瘿条 |

**② 上下文注入**（`【古今·中西医病名对照】`）

```
· 消渴（别名：消瘅） 古/中医 ⇒ 今/西医 糖尿病：以上就是消渴，糖尿病了。
· 寒疝 古/中医 ⇒ 今/西医 疝气：而这里的寒疝不要跟西医的疝气结在一起，名字很类似，但是症状不太一样。
```

`note` 就是倪师原话，模型引用即是「有据可查」。UI 在回答下方渲染可展开的「病名对照 N 条」（`_diseaseTile`），展示 `古名 ⇒ 今名 + 原话`，用户能自己核对。

### 16.4 同名异义必须点明

这是本索引最容易被忽略的价值：**寒疝 ≠ 西医疝气**、**霍乱（古）= 上吐下泻 ≠ 今天的霍乱弧菌病**、**太阳中风（伤寒）≠ 脑中风（金匮）**。数据里这类条目的 `note` 本身就是倪师在讲差异（「名字很类似，但是症状不太一样」），persona 据此加了硬规则：

> 涉及病名时先对名再讲病：回答开头先用一句话把古名/中医名与今名/西医名对上；对照块里写「名字很类似但症状不太一样」的，必须点明差异，不要混为一谈。对照块没给的对应关系不要自己编。

### 16.5 顺带修的一处检索退化

加索引时发现 `keywordsFor` 会把「和 / 与 / 及 / 或 / 而 / 也 / 都 / 还 / 又 / 但 / 如 / 若 / 者 / 之」这类连接词拼进关键词（「寒疝和疝气一样吗」会切出「寒疝和疝」），已并入功能字黑名单。修完「寒疝和疝气一样吗」正确命中金匮寒疝篇，而不是满屏无关条文。

### 16.6 维护

- 讲稿 / 医案资产有增删改 → **必须重跑** `D:/Python310/python.exe tool/build_disease_alias_index.py`
- 想加新对照 → 先看 `tool/disease_alias_candidates.tsv`，把确认无误的关系写进 `SEEDS`，脚本会自动去找原文；找不到原文就说明倪师没这么讲过，宁缺勿造
- 验证：`flutter test test/disease_alias_index_test.dart`（10 条，含「每条 note 必须逐字回溯到 src 文件」这条硬断言）

## 十七、darwin 优化：用医案训练「症状 → 方证」的准确性（2026-11-07）

用户要求「用 App 里的医案资料优化问倪师AI，训练它对用户提出症状的解答准确性」。按 darwin-skill 的「评估 → 改进 → 实测 → 留或回滚」跑，但评估口径要改：**没有可用的模型凭据，跑不了 LLM 盲评，所以把「准确性」拆成可确定性验证的上游指标。**

### 17.1 为什么这样测

回答准不准，模型再强也受限于「正确材料有没有进入上下文」。这个上游指标可以离线、确定、可重复地量：

| 指标 | 含义 |
|---|---|
| **P1 讲稿可达** | ground truth 方剂是否出现在【讲义片段】或【方剂清单】（讲稿是权威来源） |
| **P2 医案可达** | ground truth 方剂是否出现在命中的医案里 |
| **P3 病机可达** | 医案病机的关键词片段是否落进上下文 |

ground truth 来自医案表本身：`诊断 + 病机 + 方剂` 三列，方剂用 `MedicalCase.formulaNames` 归一。抽样确定性（按步长均匀取），不手挑，避免「挑好答的」。

### 17.2 基线暴露的真问题

同子集（12 条）口径：

```
P1 讲稿可达 16% ｜ P2 医案 75% ｜ P3 病机 75%
```

**问「大肠癌怎么辨」，讲稿里「大柴胡汤」的条文根本没进上下文。** 原因：检索是按**病名**找条文，而答案在**方剂**上 —— 「讲这个病」的条文不等于「用这个方」的条文。

### 17.3 五步改进（每步单独验证）

**① 二跳检索（杠杆最大）**

医案里「诊断 → 方剂」是现成的映射。拿命中医案的方剂**回讲稿再检索一次**，把该方的原文拉进来。

⚠️ 第一次改完 P1 没有变化：因为第一轮已经把 8 条槽位填满，二跳永远轮不上。**必须给二跳预留槽位**（第一轮只取 `maxHits-3`）。补上预留后 16% → 66%。

⚠️ 第二个坑：二跳按方剂顺序填，第一首（麻黄附子细辛汤）把 3 个预留槽吃光，第二首（射干麻黄汤，才是答案）进不来。改成**轮流取**：每首方先各占 1 条，再第二轮。

**② 医案召回 3 → 5 条**

`retrieveCases` 多取 2 条，**只用于抽方，不写进 prompt**（prompt 仍只放 3 条医案）。给二跳更多候选方。

**③ 求诊话术的泛词必须停用**

「西医诊断我是里寒湿」被切成关键词后，先命中「西医」「诊断」（讲稿里遍地都是），把「寒湿」真正的医案挤掉 —— 实测命中的是肺癌案、癫痫案，全不相干。停用词加 `西医/诊断/医院/检查/患者`。

**更要紧的是改成子串判定**：只停「西医」「诊断」拦不住 4-gram 拼出来的「西医诊断」「医诊断」。改成「关键词**包含**任一停用词就丢弃」后，同一个问题的 8 条片段从「7 条是伤寒通用条辨」变成「5 条柴胡/泻心类，与少阳阳明方向吻合」。

**④ 病名索引只让古篇名参与检索**

问「大肠癌」会命中对照条目「脓血 → 大肠癌」，于是优先去检索「脓血」，把桃花汤类条文塞满上下文。改为：**只有 `gujin`（古篇名）条目的古名可以当检索词**，`zhongxi` 条目（症状 → 西医名）只做提示块，不参与检索。

**⑤ 关键词配额：首词填满，其余每词 2 条**

「大肠癌」在讲稿命中少时，会由「大肠」把剩余槽位全部吃掉（大肠经、针灸条文）。改为首个命中的词才允许填满，其后每词最多 2 条 —— 既保住「咳嗽」这类单词提问能拿满 8 条，又不让短词泛滥。

### 17.4 persona：从「有材料」到「答得准」

材料齐了还得会答。新增三条硬规则（`tool/gen_llm_persona.py` → `assets/llm/persona.md`）：

1. **症状型提问固定五步走**：归纳主症 → 定六经/金匮篇目 → 方证名 + 首选方 1–2 首（附出处） → 鉴别为什么不是相邻方证 → 引用同病机医案（写「医案 #序号」）
2. 🔴 **禁止把片段/方剂清单整串罗列** —— 那些是检索材料，不是答案
3. 🔴 **禁止复述医案里的剂量、克数、丸数、服法** —— 上下文现在会带出「温经汤8+炮附子1…三餐饭前各八颗」，照抄会害人；只讲辨证思路与方名

第 3 条是这次改动**新引入的风险**：医案进上下文带来的副作用，必须同时堵住。

### 17.5 结果

同子集（12 条）口径，可直接对比：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| P1 讲稿可达 | **16%** | **100%** |
| P2 医案可达 | 75% | 100% |
| P3 病机可达 | 75% | 100% |

扩大样本（60 条，抗抽样偏差）：**P1 91% / P2 88% / P3 93%**。

未命中的 5 条都是「诊断列写的是病机而非病名」（肺中有痰 / 阳明经热 / 上热下寒 / 上焦湿热 / 西医查有胆结石），属医案表本身的粒度问题。

已固化为回归测试 `test/llm_case_accuracy_test.dart`（60 条样本 + 阈值 P1≥85 / P2≥80 / P3≥85，并在 persona 变更时断言三条安全规则仍在）。

### 17.6 已知限制（未验证的部分）

- **没跑真实模型**：本机没有可用的 LLM 凭据（Qoder 本地端点 `127.0.0.1:57895` 在跑但返回 401）。所以「上下文里有正确材料」已验证，「模型据此答对」尚未盲评。
- 补齐方式：拿到端点密钥后，用同一批 60 条样本跑真实生成，让独立 judge 对照医案原文判「方证是否正确」，这一步才是 dim8 的完整版。

## 十九、第三跳（症状 → 穴位 → 医案）+ 真实模型端到端评测（2026-11-07）

### 19.1 第三跳：为什么需要它

§18 之后，针灸提问能从「针灸讲稿 + 穴位库 + 医案针灸列」拿到材料，但仍有一个洞：**针灸讲稿是按经络腧穴组织的，不是按病证**。问「失眠扎什么穴」，讲稿里只有零散提到失眠的篇（任脉/督脉/足阳明胃经），拿不到完整配穴。

第三跳换条路：

```
症状词 ──(穴位库 clinicalNotes 主治)──> 候选穴位 ──(医案针灸方案)──> 用过这些穴的真实案例
```

穴位库给定位与手法，医案给配穴与病机，互补。实现是 `LlmService._jumpByAcupoints`，接入在「医案针灸列反查」**之前**（顺序反了会被随手一条医案的配穴占满 3 个名额 —— 实测问带状疱疹给的是下关/合谷/胆石点）。

穴位排序按「主治里的命中次数」降序：穴位表按经络排，直接取前 3 会混进只顺带提一句的（「失眠」曾给出大陵 + 小海 + 太乙，后两个不对症）。

### 19.2 顺带修的两处召回缺陷

**① 医案召回按词长加权**

原来按「命中关键词个数」计分。实测「带状疱疹后遗神经痛」召回的 5 条里**没有一条是带状疱疹** —— 一堆只沾了「痛」字的案例把真凶挤掉了。改为按命中词**长度**累加，并对「主要诊断」字段命中额外 ×2（诊断对上就是同病，比病机顺带提到靠谱）。

同分时按诊断长度升序（越短越像「就是这个病」）、再按 seq 兜底 —— `List.sort` 不稳定，不给次键每次召回顺序都会漂。

修完：`#299`（诊断就是带状疱疹、配穴公孙/内关/神门/关元/三阴交）从第 6 名外进到第 2 名，GT 穴位 3 个进上下文。

**② 提示词里的「诊断为空」样本**

医案表里有相当一部分是复诊记录，「主要诊断」列为空。用它们做评测会出现「西医诊断我是，针灸怎么取穴」这种零信息提问 —— 测出来的是评测集缺陷，不是能力。两个评估测试的筛选条件都补上「诊断非空 + 排除复诊噪声词」。

### 19.4 一次差点误判的经历

第一版评测集用了 #345 / #357，两题都是 ✗。逐个查上下文才看清：

- **#345**：GT 穴位其实**已经在上下文里**（上巨虚、足三里），是模型没提 —— 但该案「诊断」列为空，提问只能是「我乳房有硬块」，召回靠的是关键词，命中的是别的案，GT 本身就选得不合理。
- **#357**：「诊断」列为空，GT 穴位一个都没进上下文。

**结论：先怀疑评测集，再怀疑代码。** 换掉这两题后两个模型都是 6/6。这条教训值得记住 —— 判据错了，后面所有 keep/revert 都是错的（darwin Phase 1.5 同一句话）。
