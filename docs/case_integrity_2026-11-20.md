### 已修：2 行「必错」的根因与修正

源 sqlite 的日期原文混用两种写法，生成 md 时一律按 `MM/DD/YY` 解释，遇到 `YY/MM/DD` 就产出越界年份。

| srcrow | 患者 | `date_raw` | 原 `date`（错） | 序列位置要求 |
|---|---|---|---|---|
| 302 | 082S1V,M | `08/03/05` | 2005-08-03 | 第 1 诊 |
| 303 | 082S2V,M | `2008/3/21` | 2008-03-21 | 第 2 诊 |
| **304** | 082S3V,M | **`08/05/16`** | **2016-08-05** | 第 3 诊 → 应在 2008-03 与 2008-05 之间 |
| 305 | 082S4V,M | `2008/05/28` | 2008-05-28 | 第 4 诊 |

`08/05/16` 按 `YY/MM/DD` 读 = **2008-05-16**，恰好落在 S2 与 S4 之间。按 `MM/DD/YY` 读 = 2016-08-05，既越界又打断序列。

`Lin,Li` 同类证据：同患者、同为「29岁 娇小」、同方「肾着汤」的两条记录，一条 `03/20/08` → 2008-03-20，另一条 `08/03/13` → 2013-08-03。后者按 `YY/MM/DD` = **2008-03-13**，与前者相差 7 天（一周内复诊），按 `MM/DD/YY` 则相差 5 年且患者年龄不变。

**影响面 18 个 md 文件（医案上 9 + 医案下 9），去重后只有 2 类**：

```
08/05/16  →  2008-05-16   医案上 srcrow 304, 1049；医案下 0098, 0888
08/03/13  →  2008-03-13   医案上 srcrow 463, 616, 896, 1022, 1024, 1171, 1173
                          医案下 0239, 0384, 0386, 0428, 0735, 0992, 0994
```

其余 42 条 `(2,2,2)` 型 `date_raw` 解析结果都落在 2000–2012 内，没问题。

**为什么必须连「医案下」一起改**：`fill` 用 `(code, date)` 判断下册里哪些是独有，只改上册会让这 2 条变成 2 份「下册独有」，下次回填被当新案补入。

**为什么改 md 而不改 `to_iso()`**：`fill_medical_cases_from_md.py:read_md()` 取的是 md 的 `date` 字段（已是二手计算结果），不是 `date_raw`，所以改 `to_iso()` 完全无效。正确入口是 md 的 `date:` 与 `title:`（title 第二段是日期，H1 同）。

**已执行**：18 个文件的 `date:` / `title:` / H1 / 文件名四处同步改为新日期（`date_raw` 保留原文不动，它是真相）；App 表 `#1318` → 2008-05-16、`#1343` → 2008-03-13。改完重跑 `fill` dry-run 得「回填 0 / 新增 0 / 已补跳过 891 / 医案下独有 0」——幂等与上下册对应关系均成立。

**没动 `08/03/05`（082S1）**：按 `YY/MM/DD` 读是 2008-03-05、按 `MM/DD/YY` 读是 2005-08-03，两种读法都不越界、都能自洽（这组记录的年龄本身就不自洽：S1 记 32 岁，S4 晚 3 年却记 31 岁），没有硬证据就不猜。

## 二、串行：App 表内无串行

三节检查（标记 vs 患者性别 / 正文语汇 vs 患者性别 / 源语料自身）全部收敛到 0。中途查证的 3 项全部是**源语料瑕疵，App 侧值正确**，已写入脚本的 `KNOWN_SRC_FLAW` 白名单并附判定依据。

### 保留：2 处误挂标记**不能删**

| 序号 | 标记 | 判定 |
|---|---|---|
| #530 | `<md:11> <md:1008>` | 内容是 060 号女患者（双侧乳癌，50岁瘦小）的方剂，`md:11` 是 165 号男患者（弱视）—— 溯源上确实误挂 |
| #590 | `<md:856> <md:1015>` | 内容属 060 号女患者，`md:856` 是 117 号男患者（肺积水）—— 同样误挂 |

两行的患者栏、方剂栏逐字核对均与 060 号源条目一致，数据本身没错，错的只是多带的一个溯源标记。

**但这两个标记删不得。** `<md:N>` 一列两用：既是溯源，又是 `fill` 的幂等指纹——`fill` 用「App 行里是否已存在该 srcrow 标记」判断这条 md 是否补过。实测：删掉后重跑 `fill` dry-run 立刻变成「回填 2」，这两条会被当成未补入，把 165 号男性弱视、117 号男性肺积水的**内容回填进这两行**——正好制造出真串行。

结论是保留标记，让体检脚本用 `KNOWN_SRC_FLAW` 白名单吃掉这 2 项假阳性。要根治得把幂等指纹从治法列挪到独立列，那是重构，等真有必要再说。

### 已定性：3 项源语料瑕疵，App 侧不动

1. **`#756` md 性别误写** —— `0899_SStephen,Nicholas` 的 front-matter 写 `性别: F`，但 Stephen / Nicholas 都是男名、病程为肝癌、App 记为「男，62岁」。App 值正确。
2. **`245W,T` 患者码被两人共用** —— 源语料里编号 245 同时指「36 岁高个男（阳明经腑热，md 0283 与 0528 是逐字相同的重复文件）」和「43 岁丰腴女（脑瘤术后，md 0284）」。App `#608` / `#671` 的患者栏与内容各自对应，无串行。
3. **`117S1SS,T` 记录里混进 060 号女性的处方** —— 就是 `#468←#1351` 那一处，App 侧已由 `case_merge_map.tsv` 的 `468 1351 ... pin=7,12` 修正。

> 注：体检脚本第四节原本按 `fill.code()` 归组，而 `code()` 会抹掉前导 0，把 `11SS,R` 与 `011C,L` 归成同一个 `11-0`。已改为按标题首段原文归组，假阳性消除（`#401` 与 `#389` 患者与标记本来就各自匹配）。

## 三、JSON 化：不改

### 体积（13 列 / 1.22 MB 复测）

| 格式 | 字节 | gzip | 相对 md |
|---|---|---|---|
| md（现状） | 1,220,891 | 443,243 | — |
| JSON 对象式（带键名） | 1,318,023 | 440,454 | **+8.0%** / gzip −0.6% |
| JSON 数组式（纯数组） | 1,159,055 | 424,175 | **−5.1%** / gzip −4.3% |

APK 内 md 经 deflate 缩放比例约 0.736（12 列时 931,960 → 685,966），换数组式 JSON 约省 45 KB。

对象式反而更大 —— 1448 条 × 12 个键名的重复开销超过了 `|` 与 `"` 的差额。只有丢掉键名的数组式才省，而数组式恰好废掉了 md 最有用的属性：**人眼可直接 review**。本轮全部合并、串行排查、性别统一、四诊拆分都是直接在 md 上完成的，换成数组式 JSON 后每次核对都要写脚本还原列名。

### CPU：解析省 7 ms，检索省 0

`flutter test` 基准（JIT，预热 8 次后取 25 次均值，复刻 `parseMedicalCaseTable` 对比 `jsonDecode` + 构造 `MedicalCase`）：

| 项 | ms |
|---|---|
| md → MedicalCase（1282 条） | 10.74 |
| json → MedicalCase（1282 条） | 3.64 |
| **差值** | **7.10** |

JIT 差 7 ms；release AOT 再快 2–3 倍 → 约 2–3 ms。`getAllMedicalCases()` 有进程内缓存，**一个进程只跑一次**。

**但真正的大头不在这里**：

| 检索场景 | ms |
|---|---|
| 首次全量 `matches('口渴')`（含 `_searchNorm` 懒构建） | **79.63** |
| 二次全量（索引已建） | 3.75 |
| **索引构建净成本** | **75.88** |

那 76 ms 发生在用户第一次敲字搜索时，是 `toSimplified` 把 1282 条全文（含四诊）逐个转成简体——**与文件格式完全无关，换 JSON 一分也省不到**。

加四诊的代价也能量出来（同一指标）：

| 版本 | 首次全量检索 | 命中 |
|---|---|---|
| 前（12 列 932 KB） | 67.12 ms | 162 |
| 后（13 列 1.22 MB） | 79.63 ms | **535** |

多花 12.51 ms（+19%），换来可检索命中 162 → 535（3.3 倍）——因为患者口语描述（「口渴爱喝温水」「三点会醒」）现在也进索引了。这笔账是划算的。

**结论：JSON 化省 7 ms 解析、检索零收益。要提高运行效率，该动的是索引构建的时机与方式，不是文件格式。**


### 真正该动的三处（已处理）

1. **3.59 MB 备份被打进包** —— `assets/medical_cases/` 下有 4 个 `.bak-*`（`bak-dup` / `bak-fill-md` / `bak-fmt` / `bak-merge`），pubspec 用的是目录声明 `- assets/medical_cases/`，会把目录下所有文件一并打包。已在 `build/unit_test_assets/` 实测确认这些 `.bak` 确实被复制为 asset。

   已挪到 `.workbuddy/backup/20261120_case_md/`（git 未跟踪该目录，可随时挪回）。**收益 3.59 MB，是换 JSON 的约 90 倍。**

2. **医案库页重复解析一遍** —— `lib/screens/medical_case_library_screen.dart:70` 自己 `rootBundle.loadString` + `parseMedicalCaseTable`，绕过了 `getAllMedicalCases()` 的缓存，导致 932 KB 字符串与 1282 个 `MedicalCase` 对象各存两份。已改为复用缓存（并移除随之空转的 `package:flutter/services.dart` import）。

3. **`<md:N>` 溯源标记直接显示给用户** —— 第 9 列（治法）一列两用：既是回填脚本的幂等指纹，又是详情页的「治法原则」。实测 **827 行带标记，其中 277 行只有标记本身**，这些行在详情页会显示成光秃秃的 `<md:1059>`。已在 `parseMedicalCaseTable` 里统一剔除（`medical_case_data.dart` 的 `_mdTag`），纯标记行清空后由详情页原有的 `isEmpty` 分支自动隐藏，无需改 UI。已加回归测试 `test/medical_case_extract_test.dart`「治法列不把 <md:N> 溯源标记漏给用户」。

### 什么时候才该上 JSON

当体检脚本与 App 需要共用同一份结构化数据、且字段增删频繁到「维持 12 列对齐」成为负担时。现在的 12 列是稳定的 —— md 表格就是那份 JSON，只是用 `|` 当分隔符，还额外送了一个人能直接读的渲染。
